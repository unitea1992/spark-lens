# リリース・ドキュメント運用

Spark Lensは公開ソースの小規模なセルフホストツールで、npmへの公開を予定しないため `package.json` の `private: true` を維持します。コードやスクリーンショットが古いままにならないよう、実際の利用者に影響するまとまりでバージョンとドキュメントを更新します。

## バージョンの方針

[Semantic Versioning](https://semver.org/lang/ja/) の `MAJOR.MINOR.PATCH` を採用します。現在は0.x（APIの構造はまだ安定化途上）です。

- **0.2.0**：今回のような監視方式・設定UI・API・表示などのまとまった後方互換な機能追加。作業中は `CHANGELOG.md` の `[Unreleased]` に記録します
- **0.2.1**：0.2.0公開後の、不具合修正やドキュメント修正のみでコードの挙動が変わらないリリース（資料だけの小さな修正は必ずしもタグ不要）
- **0.3.0**：新機能、API経路の追加、機能的に大きなUX変更
- **1.0.0**：APIの互換性方針・設定スキーマ・運用手順が十分に定まった時点。その後の破壊的変更は2.0.0などのメジャーへ

固定の日付だけでバージョンを増やさず、**複数の機能がmainに統合され、動作確認できたタイミング**で1回リリースします。更新が多ければ2〜4週間ごとにまとめ、重要な修正はその都度パッチ版で出します。0.xでも既存のエンドポイントと設定の破壊はできるだけ避けます。

## 公開前チェックリスト

1. mainで作業ブランチの差分をレビュー・マージし、CI成功を確認する。公開コード・画像に秘密情報、IPアドレス、ローカル固有のタスクやアカウントがないか確認する
2. `pnpm install --frozen-lockfile`、`pnpm check`、必要に応じて `pnpm scan:secrets` を実行する
3. 主要画面をデスクトップ・スマホで表示確認する。`docs/images/` のサンプル画像がUIと大きく異なる場合は、ダミーデータで安全に再作成する。**実際の稼働セッションや識別情報のスクリーンショットをそのまま公開しない**
4. READMEの使い方・設定例・利用可能なエンジン/API・価格の前提、公開用の変更履歴を修正する。新しいAPIは試せるcurl例、旧APIの互換性を記述する
5. `package.json` のバージョンと `CHANGELOG.md` を一致させる。`[Unreleased]` を `[0.2.0] - YYYY-MM-DD` などに確定し、次の空の `[Unreleased]` を作る
6. マージ後のmainに `git tag -a v0.2.0 -m 'Spark Lens v0.2.0'` のようにタグを付ける。タグとリリースをGitHubへ公開するかはオーナーが決める。**作業ブランチで先にタグや公開リリースを作らない**
7. アップグレード/ロールバック（設定・ユーザーサービス）が可能かチェックする。必要な設定変更はCHANGELOGに残す

## ドキュメントを古くしない運用

- **機能PRと同時**：READMEの関連段落、設定例、API、テスト、CHANGELOGの`[Unreleased]` を更新する。ドキュメント作業を後でまとめて放置しない
- **月1回程度**：READMEの掲載機能、3ページ構成、`docs/images/` の代表画面、外部価格比較リンク、依存関係のバージョン記述を確認する。古い情報は残すより更新・削除を優先する
- **リリース時**：README冒頭の導線、CHANGELOG、必要な移行手順を見直し、公開ソースの読み手が実現可能な操作だけ説明する
- **価格比較**：`models.dev` の最終確認日時・利用モデルのキー・比較プロバイダ・キャッシュ読み取り料金が現在も存在することを検証する。6時間ごとの条件付き再確認を基本とし、エラー時は古い最終価格の使用を表示する。比較先は `llms[].apiPriceAs` / `apiPriceComparison`（必要なら固定対応表）に明示し、未知のモデルに適当な価格を割り当てない

既存のREADMEは長い詳細説明も含むため、今後も新しいトップページを増やさず、必要があれば技術的な仕様を `docs/` へ分割し、READMEは導入・構成・参照リンクを中心に保ちます。

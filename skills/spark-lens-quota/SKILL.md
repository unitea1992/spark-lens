description: 複数モデル（Spark Lens に登録したクラウドのサブスクリプションとローカルLLM）へ作業を振り分ける前に、各モデルの利用枠と稼働状態を Spark Lens から確認する。実装・E2E・調査・下書きなどの作業を別モデルやサブエージェントに割り当てるときに使う。

作業を振る前に1回だけ確認する。

```sh
curl -s http://127.0.0.1:8686/api/quota
```

`127.0.0.1:8686` は Spark Lens の既定の待ち受けで、一例。自分の環境のホストとポート（`config/config.json` の `server`）に読み替える。

## 読み方

振り分け先の候補は `models[]` に並ぶものだけ。ここにないサービスには振らない。各要素は次のとおり。

- `recommendation`: `use` / `avoid_heavy` / `avoid` / `unknown`。基本はこれに従う。
- `state`: `usable` / `limited`（上限に到達）/ `loading`（ローカルLLMの読み込み中）/ `down` / `unknown`。
- `recovers_at_jst`: `limited` のとき、使えるようになる時刻。
- `tickets[]`: リセット券ごとの期限（`expires_at_jst`）と、使うのがよい時刻（`use_at_jst`）。基本は窓が満杯になる時刻。期限までに使い切れない券は、期限から逆算した時刻になり、`extra_daily_pct` にその週へ上乗せする 1 日あたりのポイントが出る。期限が近い券があると、`recommendation` が上がり `reason` に期限が出る。`use_at_jst` が 72 時間以内のときも `reason` に出る。券を使うのはオーナーの操作で、エージェントは使わない。全部、期限までに使う前提で読む。
- 長い窓（1 日以上）の `windows[].plan`: `remaining_pct`（残り）、`days_until_reset`、`daily_allowance_pct`（残り÷日数。リセットまでに使い切る 1 日の予算）、`elapsed_pct`、`pace`（`under` は経過より少ない、`on` は差が 10 ポイント以内、`over` は進みすぎ）。`reason` に「余りそう。割り振りを増やしてよい」とあるときは、窓の後半で、使用が経過より明らかに少ないか、最近のペースでリセット時に90%以下で終わる見込みで、配分を増やしてよい。`recommendation` の種類は増えない。`plan` の予算とペースには、プラン変更や臨時リセットより前の記録を混ぜない。
- `renews_at_jst` と `next_plan`: 次のプラン変更。設定が持っていて、その時刻がまだ先のときだけ入る。過ぎた日付は `null`。この窓のリセットより前なら、1 日の予算はその時刻までで、`projected_end_pct` は `null`。
- `windows[].projected_end_pct`: 直近24時間に使った速さが続くと、リセット時に何%か。5 時間などの短い窓も同じ。速さは、リセットや臨時リセットをまたいで数え、上限に届いていた時間とプラン変更より前は数えない。長い窓の `recommendation` はこれで決まる。上限を超える見込みのときだけ `avoid_heavy`、収まるなら使用率が高くても `use`（95%以上は `avoid`）。`null` は、まだ判断しない（記録が足りない。2時間に満たないか、リセットまでの時間の24分の1に満たない。そのうえ窓が始まって1時間たっていないか、臨時リセットかプラン変更があったとき）か、次のプラン変更が先に来る。
- `stale`: `true` なら取得が古い。値を信用せず、`avoid_heavy` 以下として扱う。「余りそう」は、取得が古いときには出ない。
- `reason`: 判断の理由。
- ローカルLLM（`kind: local_llm`）だけ、稼働中のとき次も付く。同じ口を複数のモデルで共有していることがあるので、振る前にどれが動いているかをここで確かめる。
  - `served_model`: いま答えているモデルの名前。クライアント側では、これに対応するモデル名を指定する（サーバーによっては、別の名前を指定しても黙ってこのモデルが答える）。作業の記録には、実際に答えたこのモデル名を残す。
  - `requests_running` / `requests_waiting`: 処理中と待ちの件数。待ちがあるときは、追加の作業を振らずに空くのを待つか、別のモデルへ回す。
  - `max_concurrent`: 同時に処理できる件数の上限。起動時の設定から読み、読めないときは `null`（既定値は推測しない）。`requests_running` がこれに達していれば `reason` に出て、`recommendation` は `avoid`。自分のサブエージェントや Pi を含めて、同時に使う本数は `max_concurrent` を超えない。`null` のときは待ちが出ない範囲で使う。
  - `pool_tokens` / `pool_free_tokens`（TensorFold のときだけ）: すべての会話が分け合う共有の領域の大きさと、その空き。長い会話になる作業を新しく振る前に見る。空きが会話の圧縮の発動点（Pi の GLM で約40万）より少ないうえに待ちも出ているなら、振らずに空くのを待つか、別のモデルへ回す。空きには、再利用のために保持している会話の分は含まれない。

## 使い分け

- 重い作業（実装・E2E）は `use` のモデルだけに振る。
- 軽い作業（調査・下書き）は `use` か `avoid_heavy` のモデルに振る。
- `avoid`・`unknown`・`loading` には振らない。`loading` は読み込みが終わってから送る。
- 全部が `use` でないときは、自分の枠を使い切らない側へ寄せ、`recovers_at_jst` が近いものを待つ手もある。

## 推移も見るとき

大きな作業をまとめて振る前や、配分を見直すときは、推移も読む。

```sh
curl -s 'http://127.0.0.1:8686/api/quota?days=7'   # 各ウィンドウに trend が付く
curl -s 'http://127.0.0.1:8686/api/usage?days=7'   # daily[] に 1 日ごとのトークン数と換算額
```

- `trend.rate_pct_per_hour_24h`: 直近 24 時間の消費の速さ（1 時間あたりのポイント）。速いサービスへの追加は控えめにする。
- `trend.previous_window_peak_pct`: 前回のウィンドウの最大値。100 に近いなら、前回と同じ配り方では今回も上限に届きやすい。
- `trend` が `null`、または `since` が最近なら、まだ記録が足りない。いまの値だけで判断する。

判定の基準値は応答の `thresholds` にある。入力欄をふさぐ案内など、画面上の対話待ちは検知できない。
